# 意向宝 bug 解析与优化方案（2026-11-20）

> 只读审查的结果：审查过程没有改动任何代码、配置或数据。基线提交 `56fe0c7`。

结论：现有测试全绿，但有 8 个会直接影响真实试点的问题（1 个安全、4 个数据正确性、3 个会让流程卡死或失败），建议先修这批。

## 检查范围与可信度

- **读了什么**：`server/app/` 全部后端模块、`app/` 全部前端文件、启动脚本、迁移、测试结构。
- **跑了什么**：后端 pytest 347 通过、3 跳过、2 XPASS；前端类型检查通过；lint 有配置问题（见第四部分）。
- **没跑什么**：前端构建和前端测试（会生成 `dist/`）；没接真实模型；没在 Windows 上验证。
- **核实程度**：标 ✔ 的条目已对照源码逐条确认；未标的来自分模块审查，行号可查但未二次复核。附录条目均未二次复核。

## 一、第一优先级（建议先修）

### 1. 跑 pytest 会让正式库使用仓库里公开的测试密码 ✔
- **位置**：`server/app/main.py:1706`、`server/tests/conftest.py:10-11`
- **原因**：`main.py` 末尾在模块级执行 `app = create_app()`，任何 `import app.main` 都会对默认目录 `server/data` 做迁移、种子和建用户。conftest 设了测试密码，却没把数据目录指到临时目录。
- **触发**：全新机器先跑 pytest 再首次启动，admin 和 planner 的密码就是仓库里的测试值，且不生成初始凭据文件。这实质上违反红线 1。
- **修法**：删掉模块级 `app`，启动改用 uvicorn `--factory`；conftest 强制把 `INTENT_BAO_DATA_DIR` 指向临时目录；`test_import_safety.py` 补上对 `import app.main` 的覆盖。
- **连带问题**：启动脚本生成的入口文件（`scripts/start-local.sh:170-175`、`scripts/start-local.ps1:311-316`）也因此初始化两遍。

### 2. 整份纪要作为单条材料时，意向抽取很容易直接失败 ✔
- **位置**：`server/app/services.py:2989`、`:3002`；`server/app/model_adapters.py:360-363`、`:752`
- **原因**：输出上限按“材料项数 × 220 + 512”计算。一份 TXT 或 DOCX 纪要算 1 项，上限只有 732 token，大约 3 条意向就截断；截断后的二分重试在只剩 1 项时直接抛错。
- **来源**：提交 3da8fa0（按项数估算）和 56fe0c7（按项数二分）共同引入。
- **修法**：预算取“按项数”和“按内容长度”的较大值；只剩 1 项仍超限时按文本二分（复用 `split_items_for_request` 的分片逻辑）。
- **未验证**：没接真实模型，截断是否发生取决于纪要里的意向条数。

### 3. 失败任务留下的隐藏草稿，让资料包永远到不了“已确认” ✔
- **位置**：`server/app/services.py:3961-3969`、`:3553-3561`、`:3192-3216`
- **原因**：意向观察先提交，之后身份阶段若失败，这些观察留在库里但被可见性规则隐藏。两处“待处理计数”没加可见性过滤，仍把隐藏行算进去。没有观察的说话人簇同理，会让资料包卡在“待身份校验”。
- **结果**：用户重试成功并确认完所有可见条目，资料包状态仍卡住。
- **修法**：两处计数加 `visible_observation_clause()` / `visible_speaker_clause()`；失败分支像取消一样清理本次任务的草稿。

### 4. 重跑后新旧两套观察同时出现 ✔
- **位置**：`server/app/query_visibility.py:17-27`、`server/app/services.py:2699-2769`
- **原因**：可见性只要求来源任务“已完成”，没有“被新任务取代”的概念。
- **结果**：强制重跑后，旧草稿和新草稿都进待确认列表、导出和计数。
- **修法**：新任务成功时把同包旧任务的未确认观察标记为被取代，或可见性只取最新成功任务加已确认的历史行。

### 5. 重跑后新观察会挂到已人工确认的说话人身上 ✔
- **位置**：`server/app/services.py:2091-2098`、`:2151-2154`
- **原因**：文本材料的说话人标签是 `Speaker {序号}`，按标签在整个资料包范围内复用。
- **结果**：第一次把 `Speaker 2` 确认为“采购”，重跑后另一个人的话也挂到这个已确认身份上，身份校验被绕过。
- **修法**：标签带任务作用域（音频链路 `services.py:1784` 已经这么做），或给 `SpeakerCluster` 加 `analysis_run_id`。

### 6. 数据字典原样重新导入，3×3 矩阵变成 6×6 ✔
- **位置**：`server/app/seed.py:108`、`:122`；对比 `server/app/taxonomy_service.py:351`、`:368`、`:513`、`:523`
- **原因**：种子数据用 `normalize_menu_value`（保留大小写，得到 `27QHD`），导入服务用 `normalize_taxonomy_key`（转小写，得到 `27qhd`），两边 key 对不上，唯一约束也拦不住。
- **结果**：导入一份与现状完全相同的 Excel，会新建重复的规格值和平台。这破坏红线 5。
- **修法**：种子改用同一个规范化函数，加一次性迁移统一存量数据，补“种子后原样导入应为零差异”的回归测试。

### 7. 前端默认 3.5 秒超时覆盖了建包、确认等写请求 ✔
- **位置**：`app/api-client.ts:66`
- **触发**：本机在跑模型分析、后端响应变慢时。
- **结果**：建包提示“创建失败”但服务端已建成，重试会重复建包；确认意向提示“未写入”但实际已提交，再试得到版本冲突。
- **修法**：写请求和全量刷新提到 15–30 秒；超时提示改为“结果未知，请刷新核对”；建包加幂等键。

### 8. 强制重跑时先取消旧任务再做校验 ✔
- **位置**：`server/app/main.py:768-782`，重试接口 `:940-960` 同样
- **结果**：新任务校验失败返回 422，但正在跑的任务已经被取消，两头落空。
- **修法**：校验通过后再取消，或放进同一事务。

## 二、第二优先级

### 数据与流程正确性
- **多个卡点被合并成一条** ✔：后端用顿号把卡点数组拼成字符串（`server/app/presenters.py:1096`），前端回传时又包成单元素数组（`app/intent-view-models.ts:213-216`、`app/api-client.ts:436-439`）。任何一次确认或保存后，两条卡点变一条。修法：前端保留 `bottlenecks: string[]`。
- **真实数据也标“模拟数据”** ✔：前端横幅（`app/intent-bao-app.tsx:421-427`、`:556`、`:5183-5194`）和后端（`presenters.py:725`、`:785`，`main.py:482`、`:501`、`:1691`，`exporting.py:179`）都写死。修法：按资料包实际数据属性渲染。
- **模拟语音适配器签名不匹配** ✔：`server/app/audio_adapters.py:100-106` 少了 `duration_ms` 参数，而调用方（`services.py:1683`）固定传它。模拟数据包里只要有录音，音频链路就走不通。
- **身份辅助阶段任何失败都让整次分析失败**：意向已抽完，身份推荐一超时就全盘作废（`services.py:1328-1338`）。建议降级为“带警告完成”。
- **并发确认会产生两条当前正式状态**：先读后比版本号（`services.py:3575`），没有原子校验；`formal_intent_statuses` 也没有唯一约束兜底。双击即可触发。
- **同一资料包可并发建多个分析任务**：存在性检查只匹配同模型，且与插入不在同一事务（`services.py:2699-2711`）。已有“已完成”任务时即使后来上传了新文件也直接复用。
- **字幕文件内容送模型两遍**：SRT 和 VTT 既作为整文件又作为逐条片段进入材料（`services.py:321`、`:885-903`），成本翻倍且可能产出重复观察。
- **上传不看资料包状态**：分析中或已确认的包上传后状态被改回“待预检”（`services.py:2666-2667`）。
- **PATCH 显式传 `null` 返回 500**：`main.py:690-694`、`:1335-1339`、`:1395-1400`。

### 前端交互
- **离开上传页后分析监听全部中止** ✔：`app/intent-bao-app.tsx:1033-1039`、`:1078-1089`。切到别的页面等待，不会有完成提示，数据也不刷新。
- **分析已启动却报“启动失败”** ✔：启动成功后的刷新一旦出错，就跳过了监听（`:1383-1392`、`:1199-1208`）。
- **刷新没有请求序号保护**：较早发出的轮询响应后到，会把状态改回旧值（`:4933-4939`）。
- **身份校验的未保存编辑被任何一次刷新冲掉**：`:1940-1954`。
- **评测金标准解析会整行错位** ✔：先 `trim()` 再按 Tab 切分（`:2431-2435`），行首为空的列被吃掉；原文含换行或 Tab 时一条记录被拆成多行。
- **建包的客户、职能、项目写死在前端**：`app/api-client.ts:47-61`、`:567`。另外默认技术按 `"Mini LED"` 查找（`intent-bao-app.tsx:3336`、`:3618`），而种子里叫 `MiniLED背光`，永远命中不了 ✔。
- **上传固定 120 秒超时且无进度**：`app/api-client.ts:605-606`，规格允许单文件 2GB。

### 启动与运维
- **改前端端口后全部请求失败** ✔：CORS 白名单写死 3000 和 5173（`main.py:297-308`），但脚本允许改端口。
- **`start-local.sh` 会写坏 pid 文件** ✔：只补启动前端时，后端的 pid 被覆盖为空（`:216-217`），之后停不掉。
- **`stop-local.sh` 0.3 秒后必发 `kill -9`** ✔：只按进程名校验（`:31-37`），可能误杀；后端也来不及正常收尾。
- **首次启动后整个进程没有日志**：迁移时 `server/migrations/env.py:13` 的 `fileConfig` 会禁用已有 logger。修法：`disable_existing_loggers=False`。
- **macOS 上数据目录没有权限收紧**：`server/app/filesystem_security.py:82-83` 非 Windows 直接返回。
- **整段音频临时文件从不删除** ✔：`services.py:1514`、`:1521`，属于敏感音频长期滞留；ASR 断点目录和迁移备份也只增不减。
- **Windows 中文系统上 ffmpeg 输出解码可能抛错**：`media_processing.py:131-146`、`:287-306`、`:328-348`、`:377-418` 用 `text=True` 按本地编码严格解码。未实机验证。
- **Windows 入口文件路径含单引号时启动失败**：`scripts/start-local.ps1:308-309`。

## 三、优化方案

### 性能（收益最大）
- **资料对齐调用数是叉积**：约“片段数 ÷ 4 × 候选数 ÷ 8”次模型调用（`services.py:1095-1118`）。1 小时会议估算上千次。建议先按时间邻近和关键词预筛，再交给模型。
- **意向抽取每批最多 6 项**：默认输出上限 2048 下 (2048−512)÷220 取整为 6。长会议要上百次调用，每次都重发全量主数据。建议把相邻转写片段先按时间窗合并，并只发本批用得到的主数据。
- **只有语音转写有断点**：其他阶段失败后要全部重做。建议意向结果按批落盘，分离、OCR、对齐按文件哈希缓存。
- **`/api/bootstrap` 全量加载且有 N+1**：每条观察 6–10 次查询（`presenters.py:830-1333`），前端每 4 秒轮询一次。建议批量预取、分页，并给轮询换一个轻量状态接口。
- **SQLite 没开 WAL 和 `busy_timeout`** ✔：`server/app/database.py:17-25`。两行 PRAGMA 即可。
- **上传在异步路由里做同步磁盘读写**：`services.py:2617-2634`，大文件上传期间其他请求卡顿。

### 识别质量
- **关键帧只取前 20 个场景切换，且缩到 960 宽再 OCR** ✔：`media_processing.py:396-400`、`services.py:1872`。长录屏后半段没有画面证据，中文小字识别差。建议按时长均匀配额，用原分辨率。
- **语音按固定 30 秒硬切**：`services.py:70-83`，边界字词会被切断。可在静音处切。
- **说话人分离整段读入内存**：`diarization.py:137`，100 分钟约 384MB，聚类是平方级。建议分片读取、分块聚类。
- **`.m4a` 不转码直接送分离**：`diarization.py:133-143`，依赖系统 PATH 上的 ffmpeg，失败后静默降级为无说话人标签。
- **评测只取同一原话里置信度最高的一条**：`evaluation.py:90`。一句话对应多个职能时准确率被系统性压低，也没有多抽的计数。
- **VTT 解析把 cue 编号和说话人标签混进正文**：`media_processing.py:256-258`，影响证据原文定位。

### 前端工程
- **拆分 5352 行主文件**：内部已按页面划分，可机械拆成 `pages/`、`components/`、`hooks/`、`constants.ts`。把数据集刷新和分析监听提到外壳的 hook 里，可顺带解决“离开页面监听中止”和“旧响应覆盖”两个问题。
- **轮询策略**：加失败退避、页面隐藏暂停、终态即停，合并成单一轮询源。
- **加全局错误边界**：目前后端返回未知枚举会整页白屏。
- **启动脚本改跑生产构建** ✔：现在跑的是 `vinext dev`（`scripts/start-local.sh:196`、`start-local.ps1:334`）。
- **清理模板残留**：`app/chatgpt-auth.ts`、`db/`、`drizzle/`、`examples/d1/`、`worker/` 都没有运行时引用。`app/mock-data.ts` 只被测试当字符串读 ✔，且已与种子数据不同步。

### 安全加固
- **红线 4 的服务端门禁**：目前只靠“模型地址必须是回环”保证，没有按数据属性做模型白名单（`model_settings.py:47-90`）。
- **依赖未锁定**：`server/requirements.txt` 全是范围约束，pytest 混在运行时依赖里。
- **关闭生产环境的 `/docs`**，`/api/health` 不回显模型名。
- **viewer 角色**：`/api/bootstrap` 只要求登录，viewer 仍能拿到全部未确认草稿；前端只是隐藏了页面。
- **PBKDF2 迭代数**：`auth.py:31` 当前 260,000，可提高到 600,000 并在登录成功时重新哈希。
- **真实试点库也会被注入演示数据**：`main.py:220` 默认 `seed=True`，没有开关。

## 四、测试与文档

- **两个 `xfail` 标记已过期**：`server/tests/test_api.py:471` 和 `:691` 现在实际通过，应去掉标记或核对当初的遗留问题是否已解决。
- **lint 配置漏了忽略项**：`pnpm lint` 报 10144 个问题，几乎全来自 `runtime/` 的构建产物和 `server/.venv/`。源码本身只有 1 个 error（`tests/helpers/component-harness.mjs:21`）和 1 个 warning。`eslint.config.mjs` 里忽略的 `build/**` 反而是源码目录。
- **前端测试偏脆弱**：`tests/rendered-html.test.mjs` 有 123 处断言，多数是对源码字符串做正则匹配，约束不了行为，也测不到竞态问题。建议组件层换 vitest + Testing Library。
- **AGENTS.md 的数字过期**：写的是后端测试 124 项，实际 352 项。
- **4 个未提交的测试文件改动只是换行符差异**，内容没变。

## 五、建议的修复顺序

1. **第一批**：第一部分的 8 条，再加 SQLite 的两行 PRAGMA。多数是小范围改动。
2. **第二批**：第二部分的数据正确性和启动脚本问题，每条补一个回归测试。
3. **第三批**：性能优化，先做资料对齐预筛和意向分批合并，这两项决定长会议的总耗时。
4. **第四批**：前端拆分和测试方式改造，放在功能稳定之后。
