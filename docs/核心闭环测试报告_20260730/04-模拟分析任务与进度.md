# 04－模拟分析任务与进度测试报告

## 1. 测试结论

**结论：部分实现。**

模拟资料包可以生成8个阶段任务；阶段顺序、状态、进度、起止时间、尝试次数和数据库输出哈希会持久化，任务轮询接口、非强制幂等和强制新运行均有效。

但分析在HTTP请求中同步完成，返回202时全部阶段已经100%，没有独立Worker、真实过程进度、取消、分阶段重试或断点恢复。注入失败后，资料包会变为“处理失败”，但阶段任务仍停留在“处理中／待处理”且没有错误信息；服务重启也不会处理遗留任务。

## 2. 《05方案》需求映射

- 6.1～6.2：端到端阶段顺序。
- 9.1：可恢复、低资源、单任务。
- 9.4：持久化任务表＋独立Worker；阶段、进度、耗时、输入输出、错误、重试、版本和取消记录。
- 11.1、11.4：处理失败／取消、重试和幂等。
- 12.3：任务进度、当前阶段、整体进度、耗时、组件来源和失败修复。
- 13.1 Processing Orchestrator。
- 13.2：长任务只创建任务并返回ID。
- 14.1、14.3、14.6：无需保持页面、重启恢复、任务可观测。

## 3. 测试环境与前置条件

- 临时SQLite与临时文件目录。
- 分析适配器为 `mock`。
- 为验证失败持久化，测试进程临时注入一个只会抛错的适配器对象；没有修改任何源码。
- 所有失败和恢复测试只影响临时数据库。

## 6. 缺陷与建议

| 缺陷ID | 严重度 | 缺陷 | 建议 |
| --- | --- | --- | --- |
| BE-CORE-001 | 高 | 长任务同步执行，没有独立Worker | POST只写AnalysisRun和任务表并返回；Worker按单并发领取、逐阶段提交 |
| BE-CORE-002 | 高 | 重启不恢复或处置遗留任务 | 启动恢复扫描＋租约／心跳；超时任务改“待重试”，保留最近成功阶段 |
| BE-CORE-014 | 高 | 处理异常后阶段任务未标失败，也没有错误信息 | 异常事务中同时更新当前任务、后续任务和运行；记录错误类型、可重试性和修复动作 |
| BE-CORE-015 | 高 | 无取消、重试和断点恢复API | 增加任务控制资源，保存操作者、时间、原因、重试次数和阶段版本 |
| BE-CORE-016 | 中 | 任务API没有输出哈希、阶段耗时、组件／配置版本 | 扩展任务公开契约，但只返回受控元数据，不暴露文件物理路径或密钥 |
| BE-CORE-017 | 中 | 202响应实际已经同步完成，无法验证真实进度联动 | 模拟Worker也应按阶段异步更新，便于先验证页面轮询、失败、取消和恢复 |

## 7. 边界说明

- 8个阶段目前只代表模拟任务记录，不证明ASR、说话人分离、OCR、PDF／录屏对齐和意向抽取已运行。
- 本报告不测试85%准确率、60～90分钟时效、显存／内存释放或真实模型并发。
