# 09｜正式状态版本与旧会议补录测试报告

## 1. 测试结论

**结论：通过。**

人工重复确认能够追加正式版本并连接上一版本；旧版本保留且不再标记为当前；补录较早会议不会按录入时间覆盖较新的正式状态；强制重分析也不会改写正式历史。

## 4. 运行证据

### 4.1 追加版本链

```text
V2：态度5，current=true，previous=<V1 ID>
V1：态度4，current=false，previous=null
```

### 4.2 旧会议补录

正式测试用例：

```text
tests/test_api.py::test_backfilled_old_meeting_does_not_replace_current_status PASSED
```

该用例实际创建并确认2026-07-30的新会议，再创建并确认2026-06-01的补录会议；最终查询仍返回2026-07-30的正式状态为当前。

### 4.3 重分析

- 第一次分析：1个AnalysisRun
- 强制重分析后：2个AnalysisRun、16条阶段任务
- 观察数：3增至6
- 正式状态历史：重分析前后均为同一正式状态ID

## 5. 风险与后续建议

本轮未发现阻塞缺陷。后续仍建议补充：

1. 在同一天有多场会议时，明确同日期版本的业务优先级规则。
2. 补录时间落在两个既有历史版本之间的链路测试。
3. 多个客户项目映射到同一通用平台时的状态键隔离测试。
4. 历史页明确显示“会议生效时间”和“人工确认时间”，避免把补录时间误认为业务状态时间。
5. 强制重分析产生的新旧观察应按AnalysisRun分组展示，避免重复待确认项混在同一列表。
