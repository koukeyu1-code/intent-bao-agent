# 23｜人工处置到正式状态与双视角联动测试报告

## 1. 测试结论

**结论：确认、未知和退回三条主分支均通过；采用阶段与多平台／项目聚合存在高优先级错误。**

浏览器实测完成三条不同人工处置：

1. 产品洞察先修改卡点，再由产品规划负责人正式确认；
2. 采购洞察标记为“无法判断”，正式保存为独立“未知”；
3. 开发洞察退回补充，资料包回到“待补资料／待标注”。

正式确认和正式未知均进入总览、技术视角、客户视角与历史页；退回补充不进入正式看板。核心分层规则成立。

但产品洞察确认前显示采用阶段“产品项目规划”，生成的正式状态却显示“内部评估”；技术和客户看板还会把相同客户／技术／职能但不同平台或客户项目的多条正式状态压成一条，产生计数与呈现不一致。

## 5. 缺陷与修改建议

### CORE-23-01｜确认时采用阶段与正式状态不一致

- 严重度：高
- 影响：产品规划负责人看到并确认的是“产品项目规划”，看板与历史却记录成“内部评估”，会直接误导路线图判断。
- 建议：
  1. 确认API响应后断言`formal_status.adoption_stage`与提交值一致；
  2. 采用阶段实体按客户、技术、通用平台和客户项目精确写入并读取；
  3. 增加“修改建议后立即确认”的浏览器回归，防止前端使用旧对象；
  4. 在正式历史中同时记录提交值、形成的阶段状态ID和版本。

### CORE-23-02｜双视角看板丢失平台／客户项目维度

- 严重度：高
- 影响：同一客户同一技术在多个平台或客户项目上的状态会互相覆盖；顶部数量、支持者摘要和矩阵节点无法一一对应。
- 建议：
  1. 技术页最少按“客户＋平台＋客户项目”分行，再按职能分列；
  2. 客户页按“技术＋平台＋客户项目”形成独立卡片；
  3. 禁止使用`find(customer + function)`取首项；必须按完整`statusKey`聚合；
  4. 支持者和证据数量按去重后的正式状态与证据口径计算。

### CORE-23-03｜无法判断也形成正式版本，界面需解释口径

- 严重度：低
- 说明：这是合理的数据保全策略，但“正式状态数”会包含正式未知。
- 建议：指标说明明确写为“当前正式职能状态（含未知）”，另列“已判断／未知”两个子数，避免误解为9条都有明确态度。
